## Architecture: what's working

- **Module boundaries are clean.** `strava/`, `tools/`, `state_manager`, `companion`, `conversation_store`, `temporal_context` — no import cycles, each layer has a clear role.
- **State files as source of truth.** `athlete.yaml` (ruamel round-trip preserves comments), `plan.md` (locked weekly-table format), `log.jsonl` (append-only), `journal.md` (timestamped). The agent reads + writes them through tools; there's a single write path (`state_manager.append_session` et al.).
- **Tool surface coheres.** 9 tools split across 3 modules by domain. Each handler is a pure function `(args, state) -> dict`. `execute_tool` dispatcher returns errors as `{"error": ...}` instead of raising, so the agent sees and can recover from failures.
- **Strava integration self-heals.** OAuth refresh on every call (60s leeway); 401 forces refresh + one retry; 404 retries on propagation lag; subscriptions are idempotent (`ensure_subscription` kept/replaced/created); Redis backend means tokens persist across Railway redeploys.
- **`scripts/strava_setup.py status`** is the single diagnostic. Tells you env / tokens / athlete / subscriptions in one pass with actionable next-steps for each failure mode. Has already saved one debugging session (the Redis-vs-auth distinction).

## Architecture: friction + risks

### High — address before Phase 5

| # | Issue | Where | Impact |
|---|---|---|---|
| 1 | **Plan-format drift is silent.** If the agent's `update_plan` call drops the `\| Day \| Date \| Workout \| Pace target \| Notes \|` table or breaks the column order, `get_todays_workout` quietly returns `found=false`. The bot then says "no workout prescribed" with no indication anything is wrong. | `state_manager.get_todays_workout`, `tools/state._update_plan` | The `/today` fast path silently fails. User has no signal until they ask "what's my workout" and get a vague answer. |
| 2 | **No `aspect_type=update` handling.** Strava emits update events after gear assignment, name edits, or — crucially — workout_type tagging done post-upload. We ignore all of them. If user uploads an "easy run" and later marks it as "workout" in Strava, our log entry stays as `easy`. | `strava/handler.handle_event` | Mis-classified entries that don't refresh. Workaround: edit log.jsonl by hand or have the agent fix via tool calls. Not blocking but real. |
| 3 | **Concurrent log writes are unprotected.** `log.jsonl` append happens from: webhook handler thread, agent tool calls (Telegram or harness), `/log` slash command (read-only), backfill script. Python's `open('a')` is atomic at OS level for small lines on POSIX, but not guaranteed. Two near-simultaneous writes could interleave. | `state_manager.append_session` | Low probability today (one user, low rate). Will bite if Phase 5 adds a cron writing logs in parallel with webhook events. |

### Medium — fix when convenient

| # | Issue | Where |
|---|---|---|
| 4 | **`notify.py` is untested.** The async-from-sync gymnastics (asyncio.run with new_event_loop fallback) is the most likely failure point in the auto-log flow. No tests means a refactor or library upgrade could silently break Telegram pings. | `strava/notify.py` |
| 5 | **`app.py` Strava webhook routes have no tests.** `test_app.py` only covers Telegram `/webhook`. The GET `/strava/webhook` challenge verification and the POST event dispatch are exercised end-to-end in production only. | `tests/test_app.py` |
| 6 | **`cache_control` probe is per-process.** Each Gunicorn worker probes independently on first request. If the probe ever fails for a worker (network blip), that worker stays on the no-cache path until restart. Not catastrophic; just inefficient. Could persist `_cache_control_supported` to Redis. | `companion.chat` |
| 7 | **`get_recent_sessions` re-reads the full `log.jsonl` per call.** O(n). `load_full_context` calls it on every turn. Fine at hundreds of entries; would bite at thousands. | `state_manager` |
| 8 | **`MAX_TOOL_LOOPS = 8`, `MAX_HISTORY_TURNS = 10`, `REFRESH_LEEWAY_SECONDS = 60`, etc. are hardcoded.** Not env-tunable. Workable until we want to tune one in production without a deploy. | module constants across files |

### Low — note and move on

- **Single-user assumptions are baked into constants** (`SESSION_KEY`, `TOKENS_REDIS_KEY`, `USER_TELEGRAM_CHAT_ID`). Fine for now; multi-user is explicitly out of scope.
- **Strava webhook handler doesn't validate `owner_id`** matches our athlete. Since the webhook is registered against our API app's specific tokens, only our activities should arrive; defense-in-depth not critical.
- **`ruff.toml` `known-first-party` is missing `strava`** (we added the package after the last edit to ruff.toml). Imports may sort slightly differently than intended. Cosmetic.

## Observability

Working well:
- Single shared `logger = logging.getLogger("pre_coach")` from config, sub-loggers via dotted names.
- `httpx` / `httpcore` quieted to WARNING.
- Strava handler logs the propagation retry attempts at INFO (clear story in Railway logs).
- Chat-id logged on incoming messages (helps with `USER_TELEGRAM_CHAT_ID` setup).
- `status` command for one-shot diagnostics.

Gaps worth addressing later (not blocking):
- **No structured logging.** Everything is f-string interpolation. If we ever ship JSON logs for log-analysis tools, would need to migrate.
- **No metrics.** Can't tell how often `cache_control` falls back, how often Strava propagation retries kick in, what's our 5xx rate. Probably fine until we hit scale or weirdness.
- **Log levels are inconsistent.** Some `INFO` lines should be `DEBUG` (per-iteration tool calls), some `ERROR` could be `WARNING` (recoverable retries). Not urgent.

## Security

Brief pass. Concerns I looked at and resolved:

- ✓ Secrets gitignored: `.env`, `.strava_tokens.json`
- ✓ Token file mode 0600 (atomic write)
- ✓ Webhook signature on Telegram (`TELEGRAM_WEBHOOK_SECRET`); challenge verification on Strava `STRAVA_VERIFY_TOKEN`
- ✓ Strava webhook events are unsigned by design, but we mitigate by re-fetching the activity using our auth — fake events fail at fetch
- ✓ Tool calls dispatched by name from a known-good registry (`HANDLERS` dict)
- ✓ No `eval`/`exec` anywhere
- ✓ State writes go through `state_manager` only; no user input writes raw to disk

Worth flagging:
- **Refresh token in chat history.** Earlier in the development conversation, the Strava client secret was pasted in. We discussed rotating; user hasn't yet AFAIK. Worth doing once Phase 5 is settled.
- **Tokens in Redis are accessible to any process that has `REDIS_URL`.** Fine in Railway's network; would need careful thought for a shared Redis.

## Phase 5 readiness

The proactive layer needs three things we don't yet have:

1. **A non-Telegram entry point to the agent.** `companion.chat(user_message)` always writes to Redis history as a "user" turn. Cron jobs need a `companion.run_system_task(prompt) -> response` that runs the same tool-use loop but with a synthetic system message, without polluting the human conversation. Small refactor.

2. **A scheduler.** Three options:
   - Railway scheduled jobs (cleanest; one config change)
   - GitHub Actions cron (free, but the deployed app and the cron run on different infra — coordination on state files matters)
   - APScheduler embedded in the Flask app (one process, but ties cron to web-process lifetime)
   
   Lean Railway scheduled jobs.

3. **Output routing.** Cron outputs need to land in Telegram. We already have `strava/notify.send_activity_ping` — generalize it to `notify.send(text, chat_id=None)`.

Not blockers, just things to design once you decide to start Phase 5.
