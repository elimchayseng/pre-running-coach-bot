## Architecture: what's working

- **Module boundaries are clean.** `strava/`, `tools/`, `state_manager`, `companion`, `conversation_store`, `temporal_context` — no import cycles, each layer has a clear role.
- **State files as source of truth.** `athlete.yaml` (ruamel round-trip preserves comments), `plan.md` (locked weekly-table format), `log.jsonl` (append-only), `journal.md` (timestamped). The agent reads + writes them through tools; there's a single write path (`state_manager.append_session` et al.). Canonical reference: [`docs/state-schema.md`](state-schema.md).
- **Tool surface coheres.** 9 tools split across 3 modules by domain. Each handler is a pure function `(args, state) -> dict`. `execute_tool` dispatcher returns errors as `{"error": ...}` instead of raising, so the agent sees and can recover from failures.
- **Strava integration self-heals.** OAuth refresh on every call (60s leeway); 401 forces refresh + one retry; 404 retries on propagation lag; subscriptions are idempotent (`ensure_subscription` kept/replaced/created); Redis backend means tokens persist across Railway redeploys.
- **`scripts/strava_setup.py status`** is the single diagnostic. Tells you env / tokens / athlete / subscriptions in one pass with actionable next-steps for each failure mode. Has already saved one debugging session (the Redis-vs-auth distinction).

## Architecture: friction + risks

### High — address before Phase 5

| # | Issue | Where | Impact |
|---|---|---|---|
| 1 | **No `aspect_type=update` handling.** Strava emits update events after gear assignment, name edits, or — crucially — `workout_type` tagging done post-upload. Watch defaults are usually wrong; runners routinely tag a session as `Workout` or `Race` *after* the upload completes. We ignore all updates. The log entry stays as `easy` even after the user marks it `workout` in Strava. This directly undermines the workout-verification killer feature. | `strava/handler.py:75` (`handle_event` filter), `state_manager.py:155` (no `update_session_by_strava_id`) | Killer feature degraded: workouts won't be classified correctly without manual log edits. |
| 2 | **Plan-format drift is silent.** If the agent's `update_plan` call drops the `\| Day \| Date \| Workout \| Pace target \| Notes \|` table or breaks the column order, `get_todays_workout` returns `found=false` with no warning. The bot then says "no workout prescribed". | `state_manager.py:198` (`get_todays_workout` parser), `state_manager.py:266` (`_find_workout_row`), `tools/state.py:174` (`_update_plan` writer — no validation) | The `/today` fast path silently fails. User notices only when answer is vague. Audit-recommended defensive fix: after `update_plan` writes, parse for today's row and return a warning to the agent in the tool result if missing. |

### Medium — fix when convenient

| # | Issue | Where |
|---|---|---|
| 4 | **`notify.py` is untested.** The async-from-sync gymnastics (asyncio.run with new_event_loop fallback) is the most likely failure point in the auto-log flow. No tests means a refactor or library upgrade could silently break Telegram pings. | `strava/notify.py` |
| 5 | **`app.py` Strava webhook routes have no tests.** `test_app.py` only covers Telegram `/webhook`. The GET `/strava/webhook` challenge verification and the POST event dispatch are exercised end-to-end in production only. | `tests/test_app.py` |
| 6 | **`cache_control` probe is per-process.** Each Gunicorn worker probes independently on first request. If the probe ever fails for a worker (network blip), that worker stays on the no-cache path until restart. Not catastrophic; just inefficient. Could persist `_cache_control_supported` to Redis. | `companion.chat` |
| 7 | **`get_recent_sessions` re-reads the full `log.jsonl` per call.** O(n). `load_full_context` calls it on every turn. Fine at hundreds of entries; would bite at thousands. | `state_manager` |
| 8 | **`MAX_TOOL_LOOPS = 8`, `MAX_HISTORY_TURNS = 10`, `REFRESH_LEEWAY_SECONDS = 60`, etc. are hardcoded.** Not env-tunable. Workable until we want to tune one in production without a deploy. | module constants across files |

### Low — note and move on

- **Concurrent log writes are theoretically unprotected.** `state_manager.append_session` uses `open(..., 'a')` without locking. Python's append is atomic at the OS level for small writes on POSIX, but not guaranteed across edge cases (file rotation, NFS, multi-line entries near a page boundary). At one user and roughly one activity per day, this never bites. Worth revisiting *only if* Phase 5's cron stacks writes alongside webhook events at the same instant.
- **Single-user assumptions are baked into constants** (`SESSION_KEY`, `TOKENS_REDIS_KEY`, `USER_TELEGRAM_CHAT_ID`). Fine for now; multi-user is explicitly out of scope.
- **Strava webhook handler doesn't validate `owner_id`** matches our athlete. Since the webhook is registered against our API app's specific tokens, only our activities should arrive; defense-in-depth not critical.

## Observability

Working well:
- Single shared `logger = logging.getLogger("pre_coach")` from config, sub-loggers via dotted names.
- `httpx` / `httpcore` quieted to WARNING.
- Strava handler logs the propagation retry attempts at INFO (clear story in Railway logs).
- Chat-id logged on incoming messages (helps with `USER_TELEGRAM_CHAT_ID` setup).
- `status` command for one-shot diagnostics.

Gaps worth addressing later (not blocking):
- **No structured logging.** Everything is f-string interpolation. If we ever ship JSON logs for log-analysis tools, would need to migrate.
- **No metrics.** Can't tell how often `cache_control` falls back, how often Strava propagation retries kick in, what's our 5xx rate. Probably fine until we hit scale or weirdness.
- **Log levels are inconsistent.** Some `INFO` lines should be `DEBUG` (per-iteration tool calls), some `ERROR` could be `WARNING` (recoverable retries). Not urgent.

## Security

Brief pass. Concerns I looked at and resolved:

- ✓ Secrets gitignored: `.env`, `.strava_tokens.json`
- ✓ Token file mode 0600 (atomic write)
- ✓ Webhook signature on Telegram (`TELEGRAM_WEBHOOK_SECRET`); challenge verification on Strava `STRAVA_VERIFY_TOKEN`
- ✓ Strava webhook events are unsigned by design, but we mitigate by re-fetching the activity using our auth — fake events fail at fetch
- ✓ Tool calls dispatched by name from a known-good registry (`HANDLERS` dict)
- ✓ No `eval`/`exec` anywhere
- ✓ State writes go through `state_manager` only; no user input writes raw to disk

Worth flagging:
- **Refresh token in chat history.** Earlier in the development conversation, the Strava client secret was pasted in. We discussed rotating; user hasn't yet AFAIK. Worth doing once Phase 5 is settled.
- **Tokens in Redis are accessible to any process that has `REDIS_URL`.** Fine in Railway's network; would need careful thought for a shared Redis.

## Cost & token model

Rough order-of-magnitude estimate for ongoing OpenAI/Heroku Inference spend, assuming Claude Sonnet 4.6 pricing (~$3/MTok input, ~$15/MTok output) and current state-blob size.

**Per-turn breakdown (simple "what's my workout" — 1 tool call, 2 LLM round-trips):**

| | Tokens | Cost (no cache) | Cost (cache hit) |
|---|---|---|---|
| Input round 1 (system + history + user) | ~5,500 | $0.017 | $0.002 |
| Output round 1 (text + tool call) | ~500 | $0.008 | $0.008 |
| Input round 2 (above + tool result) | ~6,200 | $0.019 | $0.002 |
| Output round 2 (final reply) | ~400 | $0.006 | $0.006 |
| **Total per turn** | **~12K in / 900 out** | **~$0.05** | **~$0.018** |

Complex turns (multi-tool calls, plan edits) run 2-4× higher.

**Daily / monthly:**

| Pattern | Without cache | With cache |
|---|---|---|
| 5 simple turns/day | $0.25/day → $7.50/mo | $0.09/day → $2.70/mo |
| 10 simple + 2 complex turns/day | $0.70/day → $21/mo | $0.20/day → $6/mo |

**Cache_control is doing real work.** If Heroku ever strips the field (the runtime probe in `companion.chat` handles this gracefully but logs the fallback), expect a ~3× cost increase. Watch the warning in Railway logs over the first week.

**Growth trajectory:** The state blob is dominated by `plan.md` (~3KB) + the last 21 days of `log.jsonl` (~150 bytes/entry × ~20 entries ≈ 3KB). Total state blob caps at ~10-15KB across most usage. Doesn't grow linearly with overall log size because `get_recent_sessions` is windowed. Only `athlete.yaml` grows monotonically (race history, injury history) and it's slow.

**Verdict:** Affordable at this scale. The proactive cron in Phase 5 may add 1-2 turns/day worth of system-task LLM calls, negligible additional cost. Revisit if state blob ever exceeds ~30KB or if cache rejection becomes persistent.

## Phase 5 readiness

Three design questions need answers before Phase 5 coding starts. Tradeoffs explored below.

### Q1: Cron host — Railway scheduled jobs, GitHub Actions, or APScheduler-in-Flask?

| Option | Pros | Cons |
|---|---|---|
| **Railway scheduled jobs** | Same infra, same env vars, same Redis instance, same state files. Cron service shares the deployed code. Trivial to point at a `python scripts/cron_*.py` entry point. | Railway-specific. Mild vendor coupling. May cost slightly more (separate service hours). |
| **GitHub Actions cron** | Free at our scale. No Railway coupling. | State files in git work for *reads* but cron writes (e.g., adding to `plan.md`) need to push commits back — fragile, generates commit noise. Doesn't share Redis with the deployed app, so any state synchronization is awkward. |
| **APScheduler in Flask app** | Zero new infra. Runs in the same process as the webhook handler. | Ties cron job lifetime to Gunicorn worker lifetime — restarts/scaling can miss jobs. Concurrency story across multiple Gunicorn workers gets weird (which worker fires? lock?). |

**Recommendation:** Railway scheduled jobs. Vendor coupling is acceptable given we already deploy to Railway; the alternative options trade real reliability for cosmetic independence.

### Q2: Non-Telegram agent entry point — separate function or flag-based?

Currently `companion.chat(user_message)` always writes to Redis short-term history as a "user" turn. Cron jobs need to invoke the same tool-use loop without polluting that history (cron is not "the user").

| Option | Description | Verdict |
|---|---|---|
| **`chat_system(prompt) -> response`** | New top-level function. Builds the same system prompt + state blob, but constructs messages with a synthetic user turn that never touches Redis. Returns the assistant text for the caller to route. | **Recommended.** Clean separation. The reader of `companion.py` immediately sees "two entry points: human turns and system turns." |
| `chat(message, persist=False)` | Flag parameter. Lower API surface area. | Forces every future caller to remember the flag. Easier to misuse. |
| Cron rebuilds the loop inline | DRY violation. | Skip. |

### Q3: Notify factoring — top-level module or keep in `strava/`?

`strava/notify.py` exists today and is Strava-specific. Cron jobs will need to push messages to Telegram for the Sunday plan, morning workout reminders, etc.

**Recommendation:** factor out to top-level `notify.py` with a single `send(text, chat_id=None)` function. The async-from-sync gymnastics (asyncio.run with new_event_loop fallback) belongs in one place. Strava's `send_activity_ping` becomes a thin wrapper that formats the entry then calls `notify.send`.

This factoring is ~30 lines moved and creates the API the cron will use.

### Phase 5 shape (informal sketch — not committed)

Once the three above land:
- `scripts/cron_morning_workout.py` — reads `state/plan.md`'s today row, optionally pulls weather, calls `notify.send` to push the prescription to Telegram at 6am local.
- `scripts/cron_sunday_plan.py` — calls `chat_system("draft next week's daily table for plan.md. Consider recent fitness from get_fitness_summary. Reply with the new plan markdown plus a one-sentence rationale")`, sends to Telegram for the user to thumbs-up.
- `scripts/cron_weekly_wrap.py` — `chat_system("write a brief Sunday-evening summary of this week: miles, key sessions hit/missed, trend vs prior weeks. Tone: tight, factual, two paragraphs max")`.

None of these are blockers for current operation. Build them when you want the proactive flow.
